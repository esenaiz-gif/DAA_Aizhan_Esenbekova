# First Bad Version

## 1. Problem
У нас есть последовательность версий продукта от 1 до `n`. Известно, что после того, как в какой-то момент появляется «плохая» (сбойная) версия, все последующие версии тоже автоматически становятся плохими, так как они основаны на предыдущих. Задача состоит в том, чтобы найти самую первую плохую версию, используя как можно меньше проверок (вызовов функции проверки).

## 2. Approach
Для решения этой задачи я использовала алгоритм **бинарного поиска (Binary Search)**, так как версии упорядочены по порядку и мы знаем, что проблема идет сплошным потоком до конца. 

Ниже подробно описано, как работает каждая часть моего кода:

- `public static boolean isBadVersion(int version)`: Это вспомогательный метод-симулятор. Он принимает номер версии и возвращает `true`, если версия плохая, и `false`, если хорошая. Для примера я заложила условие, что всё начинает ломаться с версии 4 (`version >= 4`).
- `public static int firstBadVersion(int n)`: Основной метод, который ищет границу сбоя.
  - `int left = 1;` и `int right = n;` — задаем начальные границы поиска. Левая граница начинается с самой первой версии (1), а правая — с самой последней (`n`).
  - `while (left < right)` — запускаем цикл, который будет работать, пока границы не сойдутся в одну точку.
  - `int mid = left + (right - left) / 2;` — находим середину текущего диапазона. Такой способ вычисления (`left + ...`) защищает от переполнения памяти, если числа `n` будут очень большими.
  - `if (isBadVersion(mid))` — проверяем среднюю версию. Если она оказалась плохой (`true`), значит, первая плохая версия находится где-то слева от нее или прямо на ней. Поэтому мы смещаем правую границу: `right = mid`.
  - `else { left = mid + 1; }` — если средняя версия хорошая (`false`), значит, поломка где-то дальше справа. Мы сдвигаем левую границу сразу за середину: `left = mid + 1`.
- `return left;` — когда цикл завершается, указатели `left` и `right` указывают на одно и то же число. Это и есть первая плохая версия, которую мы возвращаем.
- `public static void main(String[] args)` — главный метод для проверки. В нем я задаю общее количество версий `n = 5`, вывожу пояснение и вызываю метод поиска, после чего вывожу результат на экран.

## 3. Time Complexity
**Time Complexity:** O(log n)

**Explanation:** На каждом шаге цикла алгоритм делит область поиска ровно пополам (отбрасывает половину версий). Количество необходимых проверок растет логарифмически по отношению к количеству версий `n`. Поэтому временная сложность составляет O(log n), что делает алгоритм невероятно быстрым даже для миллионов версий.

## 4. Space Complexity
**Space Complexity:** O(1)

**Explanation:** Алгоритм использует фиксированное количество простых переменных (`left`, `right`, `mid`), размер которых не зависит от размера входящих данных `n`. Дополнительная память под структуры данных не выделяется, поэтому пространственная сложность равна O(1).

## 5. Reflection / Improvement
- **Is there a more efficient approach?** Нет, для отсортированного диапазона версии бинарный поиск с O(log n) является математически оптимальным решением. Простой перебор по порядку (линейный поиск) занял бы O(n) времени, что слишком медленно.
- **What would you need to change?** Менять ничего не нужно, так как текущая реализация полностью решает задачу с оптимальной производительностью.
- **What complexity could the improved solution achieve?** O(log n) времени и O(1) дополнительной памяти.
